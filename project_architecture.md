# AtmoSync – Micro-Climate Arbitrage Analytics

## 1. Project Overview

AtmoSync is a data analytics prototype designed to monitor micro-climate conditions during the transportation of perishable agricultural products and analyze them alongside market-price information.

The system focuses on sensor parameters such as temperature, humidity, and vibration. It aims to organize this information into an analytics pipeline that can support transportation monitoring and market-opportunity analysis.

## 2. Project Objectives

- Simulate IoT sensor readings for multiple transportation containers.
- Validate sensor readings against configured prototype ranges.
- Stream sensor data using Apache Kafka.
- Store sensor and market-price data in Snowflake.
- Transform raw data into analytics-ready datasets using dbt.
- Visualize monitoring and market insights using Apache Superset.
- Explore how environmental conditions and market prices can support better transportation decisions.

## 3. Proposed Technology Stack

| Technology | Responsibility |
|---|---|
| Python | Sensor data simulation and validation |
| Apache Kafka | Real-time event streaming |
| Snowflake | Cloud data warehouse |
| dbt | Data transformation and testing |
| Apache Superset | Dashboard and data visualization |

## 4. System Architecture

The proposed AtmoSync architecture follows this data flow:

**Python IoT Simulator → Kafka Producer → Kafka Topic → Kafka Consumer → Snowflake → dbt → Apache Superset**

Market-price data is treated as a separate input source and is intended to be loaded into Snowflake for further analysis.

## 5. Component Description

### 5.1 Python IoT Simulator

The Python simulator generates synthetic sensor readings for multiple containers.

The current prototype generates:
- Temperature readings
- Humidity readings
- Vibration readings
- Timestamps
- Container identifiers
- Sensor validation status

The generated readings are stored in a CSV file named `sensor_readings.csv`.

A validation function checks whether readings fall within the configured prototype ranges.

### 5.2 Apache Kafka

Apache Kafka is planned as the event-streaming layer.

- Producer: Publishes sensor readings.
- Topic: Organizes sensor events.
- Consumer: Receives the published readings.

The planned topic name is `sensor_readings`.

### 5.3 Snowflake

Snowflake is planned as the cloud data warehouse.

It will store raw sensor readings and market-price information in separate tables for subsequent processing and analysis.

### 5.4 dbt

dbt is planned for SQL-based data transformation.

It will help:
- Clean and structure raw data.
- Create reusable transformation models.
- Calculate container-level metrics.
- Prepare analytical datasets for dashboards.

### 5.5 Apache Superset

Apache Superset is planned as the visualization layer.

Potential dashboard elements include:
- Container-wise temperature monitoring.
- Humidity and vibration trends.
- Sensor validation status.
- Market-wise commodity prices.
- Summary metrics and analytical charts.

## 6. Data Sources

AtmoSync uses multiple data categories:

1. **Synthetic sensor data:** Generated by the Python simulator for prototype testing.
2. **Market-price dataset:** Agricultural commodity market-price records used as a reference for price analysis.
3. **Reference fault datasets:** Public sensor and industrial fault datasets used for understanding sensor behaviour and fault-analysis concepts.

The reference fault datasets are not treated as actual refrigerated-container telemetry.

## 7. Data Flow

1. The Python simulator generates sensor readings.
2. The validation function checks readings against configured ranges.
3. The Kafka Producer is intended to publish readings to a Kafka topic.
4. The Kafka Consumer is intended to receive the published events.
5. Sensor events and market-price records are intended to be loaded into Snowflake.
6. dbt models will transform the raw data into analytical datasets.
7. Apache Superset will connect to the prepared data and display dashboards.

## 9. Assumptions and Limitations

- Sensor readings are currently synthetic and generated for prototype testing.
- Temperature, humidity, and vibration limits are configurable assumptions, not verified storage or transportation standards for tomatoes.
- A `VALID` status means that a reading falls within the configured prototype ranges. It does not confirm that the transported product is safe or free from spoilage.
- The market-price dataset requires verification of its date coverage, units, and source metadata before detailed price comparisons.
- The reference industrial and sensor fault datasets do not represent actual refrigerated-container conditions.
- Spoilage prediction and destination recommendations require suitable verified data, defined business rules, and validation before they can be presented as reliable results.

## 10. Expected Outcome

The expected outcome is an integrated data analytics prototype that combines simulated transportation sensor readings with agricultural market-price information and presents useful monitoring and analytical insights through an interactive dashboard.
